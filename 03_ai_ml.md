## Q1. What is Gen AI?

Generative AI is a category of AI that generates new content — text, images, code, audio — based on patterns learned from training data.

It is powered by large models such as GPT-4, Claude, Gemini, and LLaMA.

### Real-world Usage

I use Gen AI to build:

- Resume screening systems

- Code generation tools

## Q2. What is an LLM?

A Large Language Model (LLM) is a deep learning model trained on massive text data to understand and generate human language.

Examples: GPT-4, Claude, Gemini, LLaMA, Mistral, Titan

### Key Capabilities

- Text generation
- Summarization
- Question answering
- Code generation
- Translation

## Q4. What is Temperature?

Temperature controls the randomness of LLM output.

| Value | Behavior |
|-------|----------|
| 0 | Deterministic — same output every time |
| 0.7 | Balanced creativity and accuracy |
| 1.0+ | Highly creative / random |

Use low temperature for factual answers and higher temperature for creative content.

---

## Q5. What are Transformers?

Transformers are a neural network architecture that processes sequences in parallel using self-attention.

### Key Components

- Input embeddings
- Positional encoding
- Multi-head self-attention
- Feed-forward layers
- Layer normalization

### Why Better Than RNN/LSTM

| RNN/LSTM | Transformer |
|----------|-------------|
| Sequential processing | Parallel processing |
| Struggles with long sequences | Handles long-range dependencies well |
| Slow training | Faster training |
| Vanishing gradient problem | Solved via attention |

---

## Q6. What is Self-Attention?

Self-attention allows each token in a sequence to compute how important every other token is for understanding its meaning. Instead of relying only on nearby words, it builds contextual relationships across the entire sentence, helping the model resolve ambiguity and capture long-range dependencies.

### How It Works

```
Query × Key → Score → Softmax → Weight → × Value → Output
```

It helps the model understand context — e.g., which word a pronoun refers to.

## Q7. What is Fine-Tuning?

Fine-tuning is the process of training a pre-trained LLM on a smaller, domain-specific dataset to improve its performance on specific tasks.

### When to Fine-Tune

- Domain-specific language (medical, legal)
- Custom response style
- Structured output requirements
- RAG not sufficient

### Data Format

Typically JSONL format:

```json
{"prompt": "What is hypertension?", "completion": "Hypertension is high blood pressure..."}
```

### max_doc

Depends on the model's context window. Typically 512 to 4096 tokens per example.

## Q8. What are model variables, and where should we use them?

**Model variables** are the parameters or settings that control how an AI model behaves during inference or generation. They help us control the model's **output quality, randomness, length, and behavior**.

| Model Variable | What It Does | Where We Use It |
|---|---|---|
| **Temperature** | Controls randomness in the model's output. Lower values produce more deterministic responses, while higher values produce more creative or varied responses. | Use **low temperature** for RAG, factual Q&A, and data extraction; use **higher temperature** for creative tasks. |
| **Top-P** | Controls how many probable tokens the model considers when generating the next token. | Useful when we want to control output diversity without relying only on temperature. |
| **Max Tokens / Max Output Tokens** | Controls the maximum length of the generated response. | Use it when we need to control response size, cost, or latency. |
| **Top-K** | Limits the token selection to the top K most probable tokens. | Common in some open-source models and inference frameworks; not supported by every LLM provider. |
| **Stop Sequences** | Tells the model to stop generating when specific tokens or strings are reached. | Useful when generating structured or fixed-format outputs. |
| **Frequency Penalty** | Reduces the likelihood of repeatedly generating tokens that have already appeared. | Useful when we want to reduce repetitive output. |
| **Presence Penalty** | Encourages the model to introduce new topics or tokens rather than repeatedly using existing ones. | Useful for creative or exploratory generation. |
| **Seed** | Helps make model outputs more reproducible when supported by the model/provider. | Useful for testing, evaluation, and debugging. |

### Where should we use them?

The values depend on the application. For example:

| Use Case | Typical Configuration |
|---|---|
| **RAG / Question Answering** | Low temperature, controlled output length |
| **Data Extraction** | Very low temperature, structured output |
| **Chatbot** | Low-to-medium temperature |
| **Code Generation** | Low temperature for more deterministic output |
| **Creative Writing** | Medium-to-high temperature |
| **Summarization** | Low temperature |
| **Classification** | Very low temperature |

> The important point is that these variables **do not change the model's trained knowledge or architecture**. They mainly control how the model generates its response during inference.

Also, the exact variables available and their behavior can vary between **LLM providers and model architectures**, so we should always check the specific model's API documentation before configuring them.

## Q9. How does an LLM work internally?

An **LLM (Large Language Model)** is a neural network trained on large amounts of text to learn patterns, relationships, and representations of language. Most modern LLMs are based on the **Transformer architecture**.

The internal working can be understood in the following steps:

| Step | What Happens |
|---|---|
| **1. Tokenization** | The input text is broken into smaller units called **tokens**. For example, a sentence may be split into words or subwords. |
| **2. Token Embeddings** | Each token is converted into a numerical vector called an **embedding**, which represents its meaning and characteristics. |
| **3. Positional Information** | Information about the position/order of tokens is added so the model can understand the sequence of the input. |
| **4. Self-Attention** | The model determines which tokens are important to each other and learns relationships between different parts of the input. |
| **5. Transformer Layers** | The tokens pass through multiple Transformer layers containing **self-attention and feed-forward neural networks**, progressively building richer representations. |
| **6. Logits Generation** | The final representation is passed through the model's output layer to produce scores, called **logits**, for possible next tokens. |
| **7. Probability Distribution** | The logits are converted into probabilities for the possible next tokens. |
| **8. Next-Token Selection** | The model selects the next token based on the probabilities and generation settings such as temperature and top-p. |
| **9. Autoregressive Generation** | The selected token is added to the input, and the model repeats the process until it reaches the required stopping condition. |

### Example

If the input is:

> "The capital of India is"

The model processes the existing tokens and calculates probabilities for possible next tokens:

| Possible Token | Probability |
|---|---:|
| **New** | 0.01 |
| **Mumbai** | 0.05 |
| **Delhi** | 0.90 |
| **Kolkata** | 0.04 |

The model is likely to select **"Delhi"** and continue generating the response.

### What happens during training?

During training, the model is given large amounts of text and learns to **predict the next token**.

For example:

> "The capital of India is ___"

The expected next token is:

> "Delhi"

The model compares its prediction with the expected token, calculates the **loss**, and updates its weights using **backpropagation and gradient descent**.

After training, the model contains billions of learned **parameters/weights** that capture patterns and relationships learned from its training data.

> In simple terms, an LLM works by converting text into tokens, processing those tokens through Transformer layers using mechanisms such as self-attention, predicting the most likely next token, and repeatedly generating tokens to produce the final response.

## Q10. What is an SLM, and how does it work?

**SLM (Small Language Model)** is a smaller and more lightweight language model designed to perform specific tasks with **lower computational requirements, lower latency, and lower deployment cost** compared to large language models (LLMs).

| Aspect | SLM | LLM |
|---|---|---|
| **Model Size** | Smaller number of parameters | Usually much larger |
| **Compute Requirement** | Lower | Higher |
| **Latency** | Generally lower | Generally higher |
| **Cost** | Lower inference cost | Higher inference cost |
| **Deployment** | Can often run on local devices or smaller servers | Often requires powerful infrastructure |
| **Task Scope** | Usually optimized for specific or limited tasks | Better suited for broad and complex tasks |
| **Privacy** | Easier to deploy locally | May require external/cloud infrastructure |
| **Typical Use Cases** | Classification, extraction, summarization, simple chatbots, edge AI | Complex reasoning, general-purpose chat, coding, multimodal applications |

### How does an SLM work?

An SLM generally works using the same fundamental principles as an LLM. Most modern SLMs are also based on the **Transformer architecture**.

1. **Tokenization** – The input text is converted into tokens.

2. **Embedding** – Tokens are converted into numerical representations.

3. **Transformer Processing** – The tokens pass through Transformer layers where mechanisms such as **self-attention** help the model understand relationships between tokens.

4. **Next-Token Prediction** – The model predicts the most likely next token based on the input and previously generated tokens.

5. **Response Generation** – The process is repeated until the model generates the required response.

The main difference is that an SLM has **fewer parameters and is often trained or fine-tuned for specific tasks**, allowing it to provide good performance while requiring significantly fewer computational resources.

### Example

For a customer-support application, instead of using a large LLM for every request, we could use an SLM for simple tasks such as:

- Intent classification
- Sentiment classification
- Information extraction
- Simple summarization
- FAQ-based responses
- Query routing

For complex questions, we can route the request to a larger LLM.

> Therefore, an SLM is useful when we need **lower cost, lower latency, easier deployment, and task-specific performance**, while an LLM is preferred when we need broader capabilities and more complex reasoning.

## Q11. How do you identify whether a model is an LLM or an SLM?

There is **no strict universal parameter-count threshold** that officially defines whether a model is an LLM or an SLM. In practice, we identify them based on **model size, capabilities, compute requirements, and intended use case**.

| Factor | SLM | LLM |
|---|---|---|
| **Model Size** | Usually has fewer parameters | Usually has significantly more parameters |
| **Compute Requirement** | Lower | Higher |
| **Memory Requirement** | Lower | Higher |
| **Latency** | Generally faster | Generally slower |
| **Deployment** | Can often run on local machines, edge devices, or smaller GPUs | Often requires more powerful GPUs or distributed infrastructure |
| **Capabilities** | Usually optimized for specific or limited tasks | Generally designed for broader language and reasoning tasks |
| **Training Objective** | Often fine-tuned for specific domains/tasks | Usually trained for broad general-purpose capabilities |
| **Use Cases** | Classification, extraction, simple chatbots, routing, summarization | General chat, complex reasoning, coding, analysis, and broader applications |

### How do we practically identify it?

When evaluating an unknown model, we can check:

1. **Model documentation** – The model provider may explicitly describe it as a small or large language model.

2. **Number of parameters** – Parameter count gives an indication of model size, although it is not a strict definition.

3. **Hardware requirements** – If the model can efficiently run on a laptop, edge device, or a single low-resource GPU, it is more likely to be an SLM.

4. **Intended use case** – A model designed specifically for tasks such as classification, extraction, or lightweight chatbot applications is more likely to be considered an SLM.

5. **Model architecture and capabilities** – We should also consider context length, reasoning capabilities, training data, and overall model capacity.

> **Important:** SLM vs. LLM is not determined only by parameter count. A smaller model can still have strong capabilities, and the terminology is not standardized across the industry. Therefore, we should consider the **model's size, resource requirements, capabilities, and intended purpose together**.

## Q12. What is the architecture of Transformers?

The **Transformer** is a neural network architecture introduced for processing sequential data, especially natural language. Modern LLMs are primarily based on Transformer architectures.

The original Transformer consists of two main components:

| Component | Purpose |
|---|---|
| **Encoder** | Reads and understands the input sequence and creates contextual representations. |
| **Decoder** | Uses the encoded information to generate the output sequence. |

The Transformer architecture is built using several important components:

| Component | What It Does |
|---|---|
| **Tokenization** | Converts text into tokens that the model can process. |
| **Token Embeddings** | Converts each token into a numerical vector representation. |
| **Positional Encoding** | Provides information about the position/order of tokens in the sequence. |
| **Multi-Head Self-Attention** | Allows each token to focus on other relevant tokens and understand relationships within the sequence. |
| **Feed-Forward Neural Network** | Processes and transforms the representations learned by the attention mechanism. |
| **Residual Connections** | Helps information flow through deep Transformer layers and makes training more stable. |
| **Layer Normalization** | Normalizes intermediate representations and improves training stability. |
| **Output Layer** | Converts the final representations into probabilities for possible output tokens. |

### Types of Transformer Architectures

| Architecture | Description | Common Use Case |
|---|---|---|
| **Encoder-Only** | Uses only the Transformer encoder to understand and represent input text. | Classification, embeddings, semantic search |
| **Decoder-Only** | Uses only the Transformer decoder with causal/self-attention to generate text one token at a time. | Chatbots, text generation, code generation |
| **Encoder-Decoder** | Uses both encoder and decoder. The encoder understands the input, and the decoder generates the output. | Translation, summarization, text-to-text tasks |

### Example

For a modern **decoder-only LLM**, the process is approximately:

**Input Text → Tokenization → Embeddings → Transformer Layers → Self-Attention → Feed-Forward Network → Output Probabilities → Next Token**

The model repeatedly predicts the next token until the response is complete.

> The key idea behind the Transformer is **self-attention**, which allows the model to understand relationships between different tokens in a sequence efficiently, without processing the sequence strictly one token at a time like traditional RNNs.

## Q13. How does an LLM know when and which tool to use?

An LLM does not inherently know how to execute tools. The application provides the LLM with **tool definitions**, which usually contain the **tool name, description/docstring, input parameters, parameter types, and schema**.

The **docstring/description is especially important** because it tells the LLM what the tool does and helps it understand **when the tool should be used**.

| Step | What Happens |
|---|---|
| **1. Tool Definition** | We create a tool, usually as a Python function, and provide a clear **name, description/docstring, parameters, and parameter types**. |
| **2. Tool Schema** | LangChain or another framework converts the function and its metadata into a structured **tool schema** that can be provided to the LLM. |
| **3. User Query** | The user asks a question or gives an instruction. |
| **4. Intent Understanding** | The LLM analyzes the user's query and determines whether it can answer directly or needs to use a tool. |
| **5. Tool Selection** | The LLM compares the user's intent with the available **tool names and descriptions/docstrings** and selects the most appropriate tool. |
| **6. Parameter Generation** | The LLM generates the required arguments based on the tool's parameter definitions and the user's query. |
| **7. Tool Execution** | The application or agent framework executes the actual Python function. The LLM itself generally does not execute the function. |
| **8. Tool Result** | The tool returns the result to the LLM. |
| **9. Final Response** | The LLM uses the tool result to generate the final response to the user. |

### Example

Suppose we create a Python tool:

```python
@tool
def get_weather(city: str) -> str:
    """Get the current weather for a given city."""
    ...
```

Here, the docstring:

Get the current weather for a given city.

helps the LLM understand what the tool is used for.

The framework provides the LLM with information conceptually like:

| Tool Information | Example |
|---|---|
| **Tool Name** | `get_weather` |
| **Description / Docstring** | Get the current weather for a given city |
| **Parameter** | `city` |
| **Parameter Type** | `string` |

If the user asks:

> "What is the weather in Mumbai today?"

The LLM recognizes that the get_weather tool is relevant and generates a structured tool call:
```json
{
  "name": "get_weather",
  "arguments": {
    "city": "Mumbai"
  }
}
```

> The application then executes the Python function and sends the result back to the LLM.

### How does the LLM decide?

The decision is primarily based on:

1. **Tool description/docstring** – Explains what the tool does and helps the LLM determine when it should be used.
2. **Tool name** – Helps identify the purpose of the tool.
3. **Tool parameters** – Tell the LLM what inputs the tool requires.
4. **Parameter types and schema** – Help the LLM generate valid arguments.
5. **User intent** – Determines what the user is actually asking for.
6. **Available context** – Helps determine whether a tool is necessary.
7. **Model's learned ability** – The model has been trained to recognize when a tool/function call is appropriate.

> **Important:** The docstring does not directly execute or force the tool to be used. It provides information to the LLM about the tool. The LLM uses that information along with the user's query to decide whether and which tool to call.

In modern applications, this is commonly implemented using **function calling or tool calling**.

# RAG (Retrieval Augmented Generation)

## Q14. What is RAG?

RAG is a technique that enhances LLM responses by retrieving relevant documents from an external knowledge base before generating an answer.

### Pipeline

```
User Query
    ↓
Embed Query
    ↓
Search Vector DB
    ↓
Retrieve Top-K Chunks
    ↓
LLM + Context
    ↓
Response
```

### Why RAG

- Reduces hallucination
- Uses up-to-date data
- Domain-specific knowledge
- No full model retraining needed

## Q15. What is Recursive Character Text Splitter?

A chunking strategy from LangChain that splits text using a hierarchy of separators:

1. `\n\n` (paragraphs)
2. `\n` (lines)
3. ` ` (spaces)
4. `""` (characters)

It tries to keep semantically meaningful chunks together by trying larger separators first.

```python
from langchain.text_splitter import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(
    chunk_size=500,
    chunk_overlap=50
)
```

- Use relevant, high-quality documents

- Use CRAG or Self-RAG for self-correction
- Set temperature low

## Q17. What is Hybrid Search?

Hybrid search combines:

- **Dense retrieval** — semantic similarity using embeddings (cosine similarity)
- **Sparse retrieval** — keyword matching using BM25

```
Score = α × dense_score + (1-α) × sparse_score
```

### Why Hybrid

- Dense: good for meaning/context
- Sparse: good for exact keyword matches
- Combined: best of both

## Q18. What is Vectorless RAG?

Vectorless RAG retrieves context without a vector database.

Instead, it uses:

- BM25 / keyword search
- SQL queries
- API calls
- Structured data lookup

Useful when data is tabular, structured, or doesn't benefit from semantic search.

## Q19. What is CRAG (Corrective RAG) / Advanced RAG?

CRAG is an enhancement to standard RAG that adds a **self-correction loop** — it evaluates the quality of retrieved documents and corrects the retrieval if the documents are not relevant enough.

### How CRAG Works

```
User Query
    ↓
Retrieve Documents
    ↓
Relevance Evaluator (LLM or Classifier)
    ↓
[Relevant] → Generate Answer
[Ambiguous] → Web Search + Refine → Generate Answer
[Irrelevant] → Fallback / Web Search → Generate Answer
```

### Key Idea

CRAG does not blindly trust the retriever. It grades the retrieved chunks and takes corrective action:

| Retrieval Quality | Action |
|-------------------|--------|
| High relevance | Proceed to generation |
| Ambiguous | Supplement with web search |
| Low relevance | Discard and search web / fallback |

### Advanced RAG Techniques (broader category)

Advanced RAG includes improvements over naive RAG:

- **Pre-retrieval:** Query rewriting, HyDE (Hypothetical Document Embedding)
- **Retrieval:** Hybrid search, re-ranking, parent-child chunking
- **Post-retrieval:** Compression, re-ranking, CRAG self-correction
- **Generation:** Prompt stuffing, citation grounding

### Real-world Usage

I use CRAG in LangGraph pipelines where an evaluator node grades retrieved chunks and routes to a web search tool if the documents are irrelevant.

---

## Q20. What is Self-RAG?

Self-RAG is a framework where the LLM itself decides **when to retrieve**, **what to retrieve**, and **how to critique its own output** — all using special reflection tokens.

### How Self-RAG Works

The LLM is fine-tuned to generate special tokens at inference time:

| Token | Meaning |
|-------|---------|
| `[Retrieve]` | Should I retrieve? Yes / No |
| `[IsRel]` | Is this document relevant? |
| `[IsSup]` | Does the document support the generation? |
| `[IsUse]` | Is the response useful to the user? |

### Self-RAG Flow

```
User Query
    ↓
LLM decides: Retrieve? (Yes/No)
    ↓ Yes
Retrieve Documents
    ↓
LLM grades: IsRel? (Relevant/Irrelevant)
    ↓
Generate Candidate Response
    ↓
LLM grades: IsSup? (Supported/Not)
    ↓
LLM grades: IsUse? (Useful/Not)
    ↓
Final Response
```

### CRAG vs Self-RAG

| CRAG | Self-RAG |
|------|----------|
| External evaluator judges retrieval | LLM judges itself via reflection tokens |
| Corrects retrieval with web search fallback | Decides retrieval need at each step |
| Easier to implement in LangGraph | Requires fine-tuned model |
| Good for production pipelines | More research-oriented |

### Real-world Usage

Self-RAG is useful when you want the LLM to be more selective about retrieval — avoiding unnecessary lookups and generating directly when it already knows the answer.


## Q22. Types of Chunking

| Type | Description |
|------|-------------|
| Fixed-size | Split by character/token count |

## Q29. What is reranking?

Reranking is a **second-stage retrieval process** used in RAG systems to improve the relevance of the documents retrieved for a user's query.

> The vector database initially retrieves a set of potentially relevant documents using similarity search. The reranker then evaluates the query and each retrieved document together and assigns a relevance score. The documents are then sorted based on their scores, and only the most relevant documents are passed to the LLM.

So, reranking means taking initially retrieved documents and reordering them based on their actual relevance to the query.

---

## Q30. Why is reranking useful?
1. Improves retrieval accuracy
2. Removes less relevant documents
3. Provides better context to the LLM
4. Helps reduce irrelevant information in the prompt
5. Can reduce hallucinations by improving the quality of retrieved context

---

## Q31. How can we implement reranking in LangChain?

Reranking in **LangChain** can be implemented by first retrieving a set of candidate documents using a vector store and then passing those documents through a **reranker** to reorder them based on their relevance to the query.

> A common approach is to use a **Cross-Encoder reranker** such as a BGE Reranker or a Cohere Reranker. LangChain provides integrations that allow the reranker to be used as a document compressor after the initial retrieval step.

The typical implementation involves:

1. Create a vector store containing document embeddings.

2. Retrieve the top **K documents** from the vector store.

3. Pass the retrieved documents to a **reranker**.

4. The reranker scores the documents based on their relevance to the query.

5. Select the top **N most relevant documents**.

6. Pass those documents to the LLM as context.

For example, with LangChain's `ContextualCompressionRetriever`:

```python
from langchain.retrievers import ContextualCompressionRetriever
from langchain.retrievers.document_compressors import CrossEncoderReranker
from langchain_community.cross_encoders import HuggingFaceCrossEncoder

model = HuggingFaceCrossEncoder(
    model_name="BAAI/bge-reranker-base"
)

reranker = CrossEncoderReranker(
    model=model,
    top_n=5
)

retriever = vectorstore.as_retriever(
    search_kwargs={"k": 20}
)

compression_retriever = ContextualCompressionRetriever(
    base_compressor=reranker,
    base_retriever=retriever
)

docs = compression_retriever.invoke(
    "What is the company's leave policy?"
)
```
Here, the vector store initially retrieves 20 documents, and the reranker evaluates those documents and returns the top 5 most relevant documents.

> In production RAG applications, this retrieve → rerank → generate approach is commonly used because vector search provides high recall, while reranking improves the precision of the final context given to the LLM.

## Q32. What are the different types of cross-encoders and what do they do?

A **cross-encoder** takes the query and document together as input and directly calculates a relevance score. Different cross-encoder approaches are mainly differentiated by the **type of task, output, and model architecture** they use.


| Type | What it does | Output | Common Use Case |
|---|---|---|---|
| **Binary Classification Cross-Encoder** | Determines whether a document is relevant or not relevant to the query. | Relevant / Not Relevant | Document filtering |
| **Multi-Class Classification Cross-Encoder** | Classifies the query-document pair into multiple relevance categories. | Class labels | Relevance classification |
| **Regression Cross-Encoder** | Assigns a continuous relevance score to each query-document pair. | Score such as `0.0–1.0` | Reranking |
| **Multilingual Cross-Encoder** | Evaluates query-document relevance across multiple languages. | Relevance score | Multilingual RAG |
| **Domain-Specific Cross-Encoder** | Trained or fine-tuned for a specific domain such as healthcare, legal, or finance. | Relevance score | Domain-specific search |
| **LLM-Based Reranker** | Uses an LLM to evaluate and rank retrieved documents based on their relevance to the query. | Score or ranking | Advanced RAG reranking |

### Most Commonly Used for RAG

For RAG applications, **regression-based cross-encoders** are commonly used for reranking because they can assign a relevance score to each query-document pair.

For example:

| Document | Relevance Score | Rank |
|---|---:|---:|
| Document A | 0.95 | 1 |
| Document B | 0.87 | 2 |
| Document C | 0.62 | 3 |
| Document D | 0.31 | 4 |

The documents are then sorted by their relevance score, and the top-ranked documents are passed to the LLM.

## Q34. How can we process PDFs, images, and tabular data and extract text/data for RAG or chatbot applications?

We can process different file types using **document loaders, parsers, OCR, and vision models**, depending on whether the data is text-based, image-based, or structured.

| Data Type | How We Process It | Common Tools / Techniques | Output |
|---|---|---|---|
| **Text-based PDF** | Extract the text, preserve page/section metadata, clean it, and split it into chunks. | PyMuPDF, pdfplumber, Unstructured | Clean text + metadata |
| **Scanned PDF** | Convert pages into images and use OCR to extract the text. | Tesseract, PaddleOCR, Document AI | Extracted text + metadata |
| **Images** | Use OCR when the image contains text; use vision models when we need to understand objects, diagrams, layouts, or other visual information. | Tesseract, PaddleOCR, Vision LLMs | Text or structured information |
| **CSV / Excel** | Read the data while preserving rows, columns, headers, and data types. | Pandas, OpenPyXL | Structured/tabular data |
| **Tables inside PDFs** | Detect and extract the table structure instead of treating it as normal text. | Camelot, Tabula, pdfplumber, Document AI | Rows and columns |
| **Complex documents** | Combine text extraction, OCR, table extraction, and vision-based processing depending on the content. | Unstructured, Document AI, Vision LLMs | Structured text/data |

After extraction, the data is generally processed through the following steps:

1. **Extract** text or structured data from the source.
2. **Clean and normalize** the extracted content.
3. **Preserve metadata** such as file name, page number, section, table name, etc.
4. **Chunk** large text into smaller meaningful sections.
5. **Generate embeddings** for text-based content.
6. **Store the embeddings and metadata** in a vector database.
7. During a query, **retrieve the relevant chunks** and provide them to the LLM as context.

For tabular data, we should not always convert everything into plain text and store it only in a vector database. Questions involving **calculations, filtering, aggregation, or exact values** are often better handled using SQL, Pandas, or another structured-data query approach.

The main idea is to use the appropriate extraction method for each data type and then convert the extracted information into a format that the RAG system can effectively retrieve and use.

## Q35. What is OCR and how does it work?

**OCR (Optical Character Recognition)** is a technology used to **detect and convert text present in images, scanned PDFs, documents, or screenshots into machine-readable text**.

| Step | What Happens |
|---|---|
| **1. Image Input** | OCR receives an image, scanned document, or PDF page containing text. |
| **2. Preprocessing** | The image is cleaned and improved using techniques such as noise removal, resizing, deskewing, and contrast enhancement. |
| **3. Text Detection** | The OCR model identifies the regions of the image that contain text. |
| **4. Text Recognition** | The detected text regions are processed to recognize individual characters, words, and sentences. |
| **5. Post-processing** | The extracted text is cleaned and corrected to improve accuracy and formatting. |
| **6. Structured Output** | The final text can be returned as plain text, JSON, tables, or other structured formats depending on the OCR system. |

For example, if we have a scanned invoice:

> **Invoice No: 12345**  
> **Customer: John Smith**  
> **Amount: ₹50,000**

OCR can convert the visual content into machine-readable text or structured data that can then be processed by an application.

### OCR in RAG

In a RAG application, OCR is especially useful for **scanned PDFs and images** where normal text extraction does not work.

The extracted text can then be:

**OCR → Text Cleaning → Chunking → Embeddings → Vector Database → Retrieval → LLM**

Common OCR tools include **Tesseract, PaddleOCR, EasyOCR, and cloud-based Document AI services**.

## Q36. If we have a PDF with text, images, and tables in it, how can we handle that?

For a PDF containing **normal text, images, and tables**, we should use a **multimodal document-processing pipeline** instead of relying on a single PDF text extractor.

| PDF Content | How We Handle It | Output |
|---|---|---|
| **Normal Text** | Use a PDF parser to extract text and preserve page/section information. | Text + metadata |
| **Images** | Use OCR if the image contains text; use a vision model if we need to understand the visual content. | Text / Description / Structured data |
| **Tables** | Use a table extraction tool to preserve rows, columns, headers, and relationships. | Structured table data |
| **Scanned Pages** | Apply OCR to the page images to extract the text. | Machine-readable text |
| **Mixed Content** | Process each content type separately and then combine the extracted information with its metadata. | Unified document representation |

A typical approach is:

1. **Parse the PDF** and identify text, images, tables, and scanned pages.
2. **Extract normal text** using a PDF parser.
3. **Extract tables** using a table extraction tool and preserve their structure.
4. **Process images** using OCR or a vision model depending on the requirement.
5. **Combine the extracted content** while preserving metadata such as page number, section, table number, and image reference.
6. **Chunk the text and relevant extracted content** into meaningful units.
7. **Generate embeddings** for searchable text content and store it in a vector database.
8. During retrieval, **retrieve the relevant text, tables, and image-derived information** and provide them to the LLM.

For example, if page 5 contains a paragraph, a table, and an image, we should preserve their relationship:

| Content | Example | Metadata |
|---|---|---|
| Text | "Revenue increased by 20%..." | Page 5 |
| Table | Revenue by quarter | Page 5, Table 1 |
| Image | Revenue chart | Page 5, Image 1 |

This approach is important because **simply extracting all PDF content as plain text can lose table structure, image information, and the relationship between different elements on the page**.

## Q40. How to Implement Human-in-the-Loop (HITL) in LangGraph

LangGraph implements HITL using **interrupts**.

The graph pauses execution at a specific node, waits for human input, and resumes from the same point after receiving a response.

## Flow

```
Start
  ↓
Agent executes
  ↓
interrupt()
  ↓
Human reviews / approves / edits
  ↓
Command(resume=...)
  ↓
Graph continues
```

---

## Human Input in LangGraph

Human input is **not limited to Yes/No**.

It can be:

- Approval (`Yes`)
- Rejection (`No`)
- Free-text feedback
- Suggestions
- Corrections
- Structured JSON/object
- Completely edited content
---

## Key Takeaways

- HITL = Human supervision inside an AI workflow.
- LangGraph enables HITL using `interrupt()` and `Command(resume=...)`.
- Human responses can be **approval, rejection, edits, feedback, or structured data**.
- HITL is useful whenever actions are **high-risk, irreversible, expensive, or require human judgment**.

### Step 1: Add a Checkpointer

A checkpointer saves the graph's state so it can be resumed later.

```python
from langgraph.checkpoint.memory import MemorySaver

checkpointer = MemorySaver()
```

---

### Step 2: Compile the Graph with an Interrupt

```python
graph = graph.compile(
    checkpointer=checkpointer,
    interrupt_before=["sensitive_node"]
)
```

Here:

- `interrupt()` pauses the graph **before** executing `sensitive_node`.
- The graph state is automatically saved by the checkpointer.

---

### Step 3: Start the Graph

```python
config = {
    "configurable": {
        "thread_id": "user-123"
    }
}

graph.invoke(
    {"input": "Transfer $5000"},
    config=config
)
```

The graph pauses before `sensitive_node`.

---

### Step 4: Human Reviews the Request

The application can now display something like:

```
Transfer $5000 to Account XYZ?

Approve / Reject
```

The graph remains paused until a human makes a decision.

---

### Step 5: Resume the Graph

Once the human approves, resume execution using the **same `thread_id`**.

```python
from langgraph.types import Command

graph.invoke(
    Command(resume=True),
    config=config
)
```

Or pass the human's input while resuming:

```python
graph.invoke(
    Command(resume="Approved"),
    config=config
)
```

The graph continues execution from the paused node instead of starting over.

---

### Why is `thread_id` Important?

`thread_id` uniquely identifies the execution session.

When you resume the graph using the same `thread_id`, LangGraph loads the saved state from the checkpointer and continues exactly where it paused.

---

### Interview Answer

> Human-in-the-Loop (HITL) in LangGraph enables pausing a workflow at specific nodes for human review or approval. This is achieved by compiling the graph with a checkpointer and specifying interrupt points using `interrupt_before` or `interrupt_after`. The graph's state is saved, and later resumed using `Command(resume=...)` with the same `thread_id`, allowing execution to continue from the checkpoint instead of restarting.

## Q41. What is MCP (Model Context Protocol)? Have You Used It?

MCP is an open protocol developed by Anthropic that standardizes how AI applications (LLMs / agents) connect to external tools, data sources, and services.

Think of it as a **universal plug standard** for AI — instead of writing custom integrations for every tool, you build one MCP server and any MCP-compatible client (Claude, LangGraph agent, etc.) can use it.

### Core Components

| Component | Role |
|-----------|------|
| **MCP Server** | Exposes tools, resources, and prompts |
| **MCP Client** | The AI application that connects to the server |
| **Tools** | Functions the LLM can call (e.g., search DB, run code) |
| **Resources** | Read-only data the LLM can access (e.g., files, docs) |
| **Prompts** | Reusable prompt templates served by the server |

### How MCP Works

```
LLM / Agent (MCP Client)
        │
        │  MCP Protocol (JSON-RPC over stdio / SSE)
        ↓
MCP Server
        │
  ┌─────┴──────┐
Tools      Resources
(DB, APIs,  (Files, Docs,
 Code)       DB Records)
```

### MCP vs Direct Tool Calling

| Direct Tool Calling | MCP |
|--------------------|-----|
| Custom code per tool | Standardized protocol |
| Tightly coupled | Loosely coupled |
| Hard to reuse across agents | Reusable across any MCP client |
| No discovery | Client auto-discovers tools |

### Example MCP Server (Python)

```python
from mcp.server import Server
from mcp.server.stdio import stdio_server
import mcp.types as types

app = Server("my-ai-tools")

@app.list_tools()
async def list_tools():
    return [
        types.Tool(
            name="search_docs",
            description="Search internal documentation",
            inputSchema={
                "type": "object",
                "properties": {
                    "query": {"type": "string"}
                },
                "required": ["query"]
            }
        )
    ]

@app.call_tool()
async def call_tool(name: str, arguments: dict):
    if name == "search_docs":
        results = search_internal_docs(arguments["query"])
        return [types.TextContent(type="text", text=results)]

async def main():
    async with stdio_server() as (read, write):
        await app.run(read, write, app.create_initialization_options())
```

### Real-world Usage

I have used MCP to:
- Expose internal document search as a tool to Claude
- Connect AI agents to internal databases without writing custom tool wrappers
- Build reusable tool servers that multiple agents can share

### Key Benefit

MCP decouples your tools from your agent framework — the same MCP server works with Claude Desktop, LangGraph agents, and any future MCP-compatible client.

## Q45. What is good prompting vs. bad prompting?

**Good prompting** means giving the LLM clear, specific, and well-structured instructions so that it understands **what to do, how to do it, and what kind of output is expected**.

**Bad prompting** is vague, ambiguous, or incomplete, which can lead to inconsistent, irrelevant, or incorrect responses.

| Good Prompting | Bad Prompting |
|---|---|
| Clear and specific | Vague and ambiguous |
| Defines the expected task | Does not clearly define the task |
| Provides relevant context | Missing important context |
| Specifies output format | No output format specified |
| Defines constraints and rules | No clear constraints |
| Uses examples when useful | Gives no examples when the task needs clarification |
| Reduces ambiguity | Leaves too much room for interpretation |

**Example:**

**Bad Prompt:**

> "Summarize this document."

**Good Prompt:**

> "Summarize the document in 5 bullet points. Focus only on the key business findings and exclude implementation details."

So, the goal of good prompting is to **reduce ambiguity and give the model enough information to produce the desired output consistently**.

## Q46. What are the main components of a prompt?

A prompt can contain several components depending on the task. The most common components are:

| Component | Purpose | Example |
|---|---|---|
| **Role** | Defines who or what the model should act as. | "You are a customer support assistant." |
| **Goal** | Defines the overall objective. | "Help the user resolve their issue." |
| **Instructions** | Specifies what the model should do and how it should behave. | "Answer in concise bullet points." |
| **Context** | Provides information required to perform the task. | Customer details, retrieved documents, conversation history |
| **Guardrails** | Defines what the model should or should not do. | "Do not provide information that is not present in the context." |
| **Examples** | Shows the model the expected input/output behavior. | Few-shot examples |
| **Output Format** | Defines how the response should be structured. | JSON, table, bullets, etc. |

Not every prompt needs all of these components. The components should be used based on the **complexity and requirements of the task**.

## Q56. How can we implement caching in AI applications?

**Caching** in AI applications means storing previously computed results so that when the same or similar request occurs again, we can reuse the cached result instead of performing the expensive operation again.

Caching can help reduce **LLM/API costs, latency, database load, and unnecessary computation**.

| Type of Caching | What We Cache | Example Use Case |
|---|---|---|
| **LLM Response Cache** | Final LLM response for a given prompt/input | Frequently repeated questions |
| **Embedding Cache** | Generated embeddings for text | Avoid regenerating embeddings for unchanged documents |
| **Retrieval Cache** | Retrieved documents/results for a query | Repeated or identical search queries |
| **Semantic Cache** | Responses for semantically similar queries | "What is the refund policy?" and "How can I get a refund?" |
| **Database/Query Cache** | Results of expensive database queries | Frequently requested business data |
| **Document Processing Cache** | Extracted/processed document data | Avoid reprocessing the same PDF or image |
| **Tool/API Cache** | Results returned by external tools/APIs | Weather, search, product or other external API calls |

### How does LLM response caching work?

Suppose a user asks:

> "What is the refund policy?"

The application first checks the cache.

**If the result exists:**

> Cache → Return cached response → No LLM call

**If the result does not exist:**

> User Query → LLM → Response → Store in Cache → Return Response

### Semantic Caching

Exact-match caching only works when the query is exactly the same. In AI applications, we can also use **semantic caching**.

For example:

> "What is the refund policy?"

and

> "How can I get a refund?"

These queries are different strings but may have the same meaning.

A semantic cache can generate an **embedding for the new query** and compare it with previously cached queries. If the similarity is above a predefined threshold, the cached response can be reused.

### Common Technologies

Depending on the requirement, we can use:

- **Redis** – General-purpose in-memory caching
- **Memcached** – Simple distributed caching
- **In-memory cache** – Useful for small/local applications
- **Vector databases** – Can support semantic similarity-based caching
- **LangChain caching mechanisms** – Useful for caching LLM calls within LangChain applications

### Important Considerations

When implementing caching, we should consider:

1. **Cache key** – How we uniquely identify a request.
2. **TTL (Time To Live)** – How long the cached result should remain valid.
3. **Cache invalidation** – When cached information should be removed or refreshed.
4. **Semantic similarity threshold** – Important for semantic caching.
5. **Data freshness** – Avoid returning stale information.
6. **User-specific data** – Do not accidentally return one user's cached response to another user.

> In AI applications, caching is especially useful for **expensive and repetitive operations**, such as LLM calls, embeddings, document processing, retrieval, and external API calls.

## Q57. What is Redis cache, and how does it work?

**Redis (Remote Dictionary Server)** is an **in-memory data store** commonly used as a cache. It stores data in **RAM**, which allows applications to read and write data very quickly.

In AI applications, Redis can be used to cache **LLM responses, embeddings, retrieval results, API responses, session data, and other frequently accessed information**.

| Component | What It Does |
|---|---|
| **Key** | A unique identifier used to find cached data. |
| **Value** | The data stored against the key, such as an LLM response. |
| **TTL (Time To Live)** | Defines how long the cached data should remain available. |
| **GET** | Retrieves a value from the cache using its key. |
| **SET** | Stores a value in the cache using a key. |
| **Expiration** | Automatically removes cached data after its TTL expires. |

### How Redis Cache Works

Suppose an AI application receives the query:

> "What is the refund policy?"

The application first checks Redis using a cache key.

1. **Check Redis**
   - If the key exists, Redis returns the cached response.
   - This is called a **cache hit**.

2. **Cache Miss**
   - If the key does not exist, it is a **cache miss**.
   - The application calls the LLM or another expensive service.

3. **Store the Result**
   - The generated response is stored in Redis with a TTL.

4. **Return the Response**
   - The response is returned to the user.

For the next identical request:

> User Query → Redis → Cache Hit → Return Cached Response

The LLM does not need to be called again.

### Example

```python
import redis

redis_client = redis.Redis(
    host="localhost",
    port=6379,
    decode_responses=True
)

key = "refund_policy"

cached_response = redis_client.get(key)

if cached_response:
    response = cached_response
else:
    response = llm.invoke("What is the refund policy?")
    redis_client.setex(key, 3600, response)

return response
```

Here:

- `GET` checks whether the response already exists.
- `SETEX` stores the response with a **TTL of 3600 seconds (1 hour)**.
- If the cached value exists, we avoid making another LLM call.

### Redis in AI Applications

| Use Case | What We Cache |
|---|---|
| **LLM Caching** | Previously generated LLM responses |
| **Embedding Caching** | Embeddings for previously processed text |
| **Retrieval Caching** | Results returned by the retriever/vector database |
| **API Caching** | Responses from external APIs |
| **Session Caching** | User/session information |
| **Rate Limiting** | Request counts and limits |

> The main advantage of Redis caching is **low-latency access to frequently used data**, which can reduce LLM/API costs and improve the response time of AI applications.

## Q58. What is LRU (Least Recently Used) caching?

**LRU (Least Recently Used)** is a caching strategy where, when the cache reaches its maximum capacity, the item that has **not been accessed for the longest time** is removed to make space for new data.

The basic idea is:

> **Keep frequently/recently used data and remove data that has been unused for the longest time.**

| Event | What Happens |
|---|---|
| **Cache has space** | New data is added normally. |
| **Cache is full** | The least recently used item is identified. |
| **LRU item found** | That item is removed from the cache. |
| **New data** | The new item is added to the cache. |
| **Existing item is accessed** | It becomes recently used and is moved to the "most recently used" position. |

### Example

Suppose the cache can store only **3 items**:

```text
A → B → C
```

If `A` is accessed:

```text
B → C → A
```

Now B is the least recently used item.

```text
C → A → D
```

`B` is removed because it was the least recently used item.

> LRU caching is useful when the cache has limited memory and we want to keep the data that is most likely to be requested again.

---
## Q59. How can Redis be used to implement LRU caching in AI applications?

Redis can implement LRU caching by configuring a **maximum memory limit** and an **LRU eviction policy**. When Redis reaches the configured memory limit, it automatically removes keys based on the selected eviction policy.

For example, Redis can be configured with:

```text
maxmemory 1gb
maxmemory-policy allkeys-lru
```
Here:

- `maxmemory 1gb` → Redis can use up to 1 GB of memory.
- `allkeys-lru` → When memory is full, Redis removes the least recently used keys.

Example in an AI Application

Suppose we cache LLM responses:

```text
User Query
    ↓
Generate Cache Key
    ↓
Check Redis
    ↓
Cache Hit → Return Cached Response
    ↓
Cache Miss → Call LLM
    ↓
Store Response in Redis
```
> If Redis reaches its memory limit, the LRU policy automatically removes older/less recently accessed cached responses.

### Example 

```python
import redis

redis_client = redis.Redis(
    host="localhost",
    port=6379,
    decode_responses=True
)

key = "llm:refund_policy"

cached_response = redis_client.get(key)

if cached_response:
    response = cached_response
else:
    response = llm.invoke("What is the refund policy?")

    redis_client.set(
        key,
        response
    )

return response
```
With Redis configured for `allkeys-lru`, Redis manages which keys should be evicted when the configured memory limit is reached.

### Where Can We Use LRU Caching in AI Applications?

| Use Case | What We Cache |
|---|---|
| **LLM Response Cache** | Frequently requested LLM responses |
| **Embedding Cache** | Frequently reused embeddings |
| **Retrieval Cache** | Frequently requested retrieval results |
| **API Response Cache** | Frequently accessed external API responses |
| **Document Processing Cache** | Previously processed documents |
| **Model/Inference Results** | Results of expensive model computations |

> **Important:** LRU and TTL solve different problems. **LRU controls which data is removed when the cache needs space**, while **TTL controls how long a cached item is allowed to remain available**. They can be used together in an AI application.

# Multi-Agent Systems

## Q60. What are the disadvantages of a multi-agent system?

A **multi-agent system** consists of multiple AI agents that collaborate with each other to complete a task. While it can be useful for complex workflows, it also introduces additional complexity, cost, and coordination challenges.

| Disadvantage | Explanation |
|---|---|
| **Higher Cost** | Multiple agents may require multiple LLM calls, increasing API and infrastructure costs. |
| **Higher Latency** | Agents may need to communicate sequentially or wait for other agents, increasing overall response time. |
| **Complexity** | Designing, coordinating, debugging, and maintaining multiple agents is more difficult than managing a single-agent system. |
| **Coordination Issues** | Agents may misunderstand each other's outputs or perform overlapping tasks. |
| **Error Propagation** | An incorrect result from one agent can be passed to other agents and affect the final result. |
| **State Management** | Maintaining shared context, memory, and state across multiple agents can be challenging. |
| **Debugging Difficulty** | It can be difficult to identify which agent caused an incorrect result, especially when many agents are involved. |
| **Non-Deterministic Behavior** | LLM-based agents may make different decisions for similar inputs, making the overall system less predictable. |
| **Tool Conflicts** | Multiple agents may try to use the same tool or perform conflicting actions. |
| **Security Risks** | More agents, tools, and communication channels increase the potential attack surface. |
| **Difficult Evaluation** | Evaluating the performance of individual agents as well as their interactions can be complicated. |
| **Over-Engineering** | A multi-agent system may add unnecessary complexity when the task could be solved effectively with a single agent. |

> **Important:** Multi-agent systems should be used when the task genuinely benefits from **specialization, parallel processing, or collaboration between agents**. If a single agent can solve the problem reliably, a multi-agent architecture may add unnecessary cost and complexity.

## Q61. How can we test a multi-agent system?

Testing a **multi-agent system** is more complex than testing a single LLM because we need to evaluate not only individual agents but also **agent coordination, tool usage, communication, and the overall workflow**.

| Testing Area | What We Test |
|---|---|
| **Unit Testing** | Test individual agent functions, prompts, tools, and business logic independently. |
| **Agent-Level Testing** | Verify whether each agent correctly understands its role, follows instructions, and produces the expected output. |
| **Tool Testing** | Check whether agents select the correct tools and provide valid parameters. |
| **Routing Testing** | Verify whether the system correctly decides which agent should handle a particular task. |
| **Communication Testing** | Check whether agents pass accurate and complete information to other agents. |
| **End-to-End Testing** | Test the complete workflow from user query to final response. |
| **Failure Testing** | Check how the system behaves when an agent, tool, API, or LLM call fails. |
| **Guardrail Testing** | Verify that agents follow safety, access-control, and business rules. |
| **Performance Testing** | Measure latency, token usage, throughput, and resource consumption. |
| **Evaluation Testing** | Evaluate the quality, correctness, relevance, and consistency of the final response. |

### Example

Suppose we have three agents:

- **Research Agent** → Retrieves information.
- **Analysis Agent** → Analyzes the retrieved information.
- **Writer Agent** → Generates the final response.

We should test each agent independently and then test their collaboration.

For example:

> User Query → Research Agent → Analysis Agent → Writer Agent → Final Answer

We can verify:

1. Did the **Research Agent** retrieve the correct information?
2. Did the **Analysis Agent** correctly interpret the research output?
3. Did the **Writer Agent** use the analysis correctly?
4. Was the information passed correctly between agents?
5. Did the system select the correct agent at each stage?
6. What happens if one agent fails?
7. Is the final response accurate and relevant?

### Important Metrics

For production systems, we can monitor metrics such as:

| Metric | What It Measures |
|---|---|
| **Accuracy** | Whether the final answer is correct |
| **Task Success Rate** | Percentage of tasks completed successfully |
| **Tool Selection Accuracy** | Whether the correct tools are selected |
| **Agent Routing Accuracy** | Whether tasks are routed to the correct agent |
| **Latency** | Total time required to complete a task |
| **Token Usage** | Number of tokens consumed by agents |
| **Cost per Task** | Overall LLM/API cost |
| **Failure Rate** | Percentage of workflows that fail |
| **Hallucination Rate** | Frequency of unsupported or incorrect information |

> **Best practice:** Use a combination of **unit tests, agent-level tests, integration tests, end-to-end tests, failure tests, and LLM evaluation**. For LLM-based systems, maintain a fixed evaluation dataset with expected outcomes and continuously run it whenever prompts, models, tools, or agent workflows are changed.

## Q62. In a multi-agent system, where should we place evaluators?

In a **multi-agent system**, evaluators can be placed at different levels depending on what we want to evaluate. The best approach is usually to have **both intermediate evaluators and a final evaluator**.

| Evaluator Location | What It Evaluates | Example |
|---|---|---|
| **After an Individual Agent** | Checks whether a specific agent produced a correct and valid output. | Research Agent → Evaluator |
| **Between Agents** | Validates the output before passing it to the next agent. | Research Agent → Evaluator → Analysis Agent |
| **After Tool Execution** | Checks whether the tool was selected correctly and whether the returned result is valid. | Agent → Tool → Tool Evaluator |
| **Before Final Response** | Validates whether the combined information is sufficient and correct before generating the final answer. | Analysis Agent → Evaluator → Writer Agent |
| **Final Evaluator** | Evaluates the final response against the user's original request. | Final Answer → Evaluator |

### Example

Suppose we have:

**Research Agent → Analysis Agent → Writer Agent**

We can place evaluators like this:

**Research Agent → Research Evaluator → Analysis Agent → Analysis Evaluator → Writer Agent → Final Evaluator**

The **Research Evaluator** can check:

- Is the retrieved information relevant?
- Is the information sufficient?
- Are there unsupported claims?

The **Analysis Evaluator** can check:

- Is the analysis logically correct?
- Did it use the research correctly?
- Are there calculation or reasoning errors?

The **Final Evaluator** can check:

- Does the final answer address the user's question?
- Is it factually correct?
- Is it grounded in the available information?
- Does it follow the required format and guardrails?

### Evaluator as a Gate

An evaluator can also act as a **quality gate**.

For example:

**Agent → Evaluator → Pass → Next Agent**

If the evaluator returns **Fail**, the system can:

- Ask the same agent to retry.
- Send the task to another agent.
- Request additional information.
- Use another tool.
- Stop the workflow and return an appropriate response.

> **Best practice:** Place evaluators at important **handoff points** where one agent's output becomes another agent's input, and use a **final evaluator** before returning the response to the user. However, adding evaluators after every step can increase latency and cost, so they should be placed where validation provides the most value.

## Q63. How many evaluators should we use in a multi-agent system?

There is **no fixed number of evaluators** required for a multi-agent system. The number depends on the **number of agents, complexity of the workflow, risk level, and importance of each intermediate output**.

A practical approach is to use evaluators at **critical checkpoints** rather than after every single agent.

| Approach | When to Use |
|---|---|
| **One Final Evaluator** | Simple workflows where only the final answer needs validation. |
| **One Evaluator per Critical Agent/Handoff** | Complex workflows where intermediate outputs can significantly affect the final result. |
| **Multiple Specialized Evaluators** | High-risk applications where different aspects such as accuracy, safety, relevance, and compliance need separate validation. |
| **Final + Critical-Step Evaluators** | Common approach for production multi-agent systems. |

For example:

**Research Agent → Research Evaluator → Analysis Agent → Writer Agent → Final Evaluator**

Here, we do not necessarily need an evaluator after every agent. We place evaluators where an incorrect output could significantly affect the next stage.

> **Best practice:** Use the **minimum number of evaluators necessary to maintain the required quality and reliability**, because every evaluator adds additional LLM calls, latency, and cost.

## Q64. What is handoff in a multi-agent system?

A **handoff** is the process where one agent transfers a task, responsibility, or conversation context to another specialized agent because the next agent is better suited to handle it.

For example, in a customer-support system:

**Customer Agent → Billing Agent → Technical Agent**

If the user asks about a payment issue, the Customer Agent can hand off the conversation to the **Billing Agent**.

| Step | What Happens |
|---|---|
| **1. User Query** | The user sends a request. |
| **2. Current Agent Understands Intent** | The current agent determines what the user needs. |
| **3. Handoff Decision** | The agent decides that another specialized agent should handle the task. |
| **4. Context Transfer** | Relevant conversation history, user information, and task details are passed to the next agent. |
| **5. New Agent Takes Over** | The specialized agent becomes responsible for handling the task. |
| **6. Response / Further Handoff** | The agent completes the task or hands it off to another agent if necessary. |

### Example

Suppose we have:

- **General Agent** → Handles general questions
- **Billing Agent** → Handles payments and invoices
- **Technical Agent** → Handles technical problems

User asks:

> "I was charged twice for my subscription."

The flow could be:

**User → General Agent → Billing Agent → Response**

The General Agent recognizes that the query is related to billing and performs a **handoff** to the Billing Agent.

> The key idea is that **handoff transfers responsibility from one agent to another**, usually because the second agent has the appropriate specialization, tools, or permissions to handle the task.

### Handoff vs Tool Calling

| Handoff | Tool Calling |
|---|---|
| Transfers the task to another **agent** | Calls an external **tool/function** |
| Another agent becomes responsible for the task | The same agent typically continues after receiving the tool result |
| Used for agent specialization | Used to perform an action or retrieve information |
| Example: General Agent → Billing Agent | Example: Agent → `get_invoice()` |

## Q65. How does communication work between different agents?

Communication between agents happens by **passing structured messages, task information, context, and previous agent outputs** from one agent to another.

For example:

**Research Agent → Research Output → Analysis Agent → Analysis Output → Writer Agent**

The communication can contain:

- Task or instruction
- Previous agent's output
- Relevant context
- Tool results
- Conversation history
- Metadata or structured data

> In a multi-agent system, agents communicate through a shared orchestration layer, message-passing mechanism, or handoff mechanism that controls what information is passed between them.

## Q66. How do you evaluate the performance of individual agents and the overall multi-agent system?

We evaluate both **individual agents** and the **complete workflow** using agent-level testing, integration testing, end-to-end testing, and LLM evaluation.

| Level | What We Evaluate |
|---|---|
| **Individual Agent** | Accuracy, relevance, instruction following, tool selection, and output quality |
| **Agent Handoff** | Whether the correct agent is selected and the required context is transferred correctly |
| **Tool Usage** | Whether the correct tool is selected and valid parameters are generated |
| **Overall System** | Final answer accuracy, task success rate, latency, cost, failure rate, and reliability |

> **Best practice:** Evaluate individual agents independently, validate important handoffs, and then evaluate the complete multi-agent workflow using a fixed evaluation dataset and relevant metrics.

## Q67. How can we communicate with an MCP server in the cloud or remotely?

To communicate with a **remote MCP server**, the MCP client connects to the server through a supported network transport instead of running the MCP server locally.

A typical architecture is:

**LLM/Agent → MCP Client → Network → Remote MCP Server → Tools / Resources / APIs**

| Component | Role |
|---|---|
| **MCP Client** | Runs inside the AI application or agent and communicates with the MCP server. |
| **Transport** | Handles communication between the client and remote MCP server, typically using **Streamable HTTP** for remote connections. |
| **MCP Server** | Exposes tools, resources, and prompts through the MCP protocol. |
| **Authentication** | Secures the connection using mechanisms such as OAuth or other supported authentication methods. |
| **Backend Services** | The MCP server can access databases, APIs, files, or other services. |

For example:

```text
User
  ↓
AI Agent
  ↓
MCP Client
  ↓
HTTPS / Streamable HTTP
  ↓
Cloud MCP Server
  ↓
Database / API / Tool
```

The important point is that the MCP client does not need to be on the same machine as the MCP server. The MCP server can be deployed on a cloud service, and the client can connect to it remotely over the network.

> For production systems, we should also consider authentication, authorization, TLS/HTTPS, network security, rate limiting, and access control when exposing an MCP server remotely.

## Q68. What are the differences between SSE and stdio communication in MCP?

**SSE (Server-Sent Events)** and **stdio (standard input/output)** are communication mechanisms used for connecting an MCP client with an MCP server.

> **Note:** In the current MCP specification, **Streamable HTTP** is the recommended transport for remote MCP servers. SSE was used by earlier MCP implementations and may still be encountered in existing systems.

| Feature | SSE | stdio |
|---|---|---|
| **Communication** | Network-based HTTP connection | Local process communication |
| **Connection** | Client connects to a remote/server endpoint | Client starts the MCP server as a local process |
| **Typical Location** | Remote/cloud server | Same machine |
| **Data Transfer** | HTTP/SSE | stdin/stdout |
| **Internet Required** | Usually required for remote communication | No |
| **Latency** | Depends on network | Generally very low |
| **Authentication** | Can use HTTP authentication mechanisms | Usually relies on local process permissions/environment |
| **Deployment** | Suitable for remote services | Simple for local applications |
| **Common Use Case** | Cloud-hosted or remote MCP servers | Local development and local tools |

## Q69. When should we use SSE vs. stdio for MCP?

The choice mainly depends on whether the MCP server is **local or remote**.

| Situation | Recommended Transport | Why |
|---|---|---|
| **Local MCP server** | **stdio** | Simple, fast, and does not require network communication. |
| **Local development** | **stdio** | Easy to start and debug locally. |
| **Remote/cloud MCP server** | **Streamable HTTP** | Designed for network-based communication with remote MCP servers. |
| **Existing MCP system using SSE** | **SSE** | Can be maintained for compatibility with existing implementations. |
| **Multiple remote clients** | **Streamable HTTP** | Better suited for remotely accessible MCP services. |

> **Interview answer:** Use **stdio** when the MCP server runs locally as a process. For a **remote/cloud MCP server**, use **Streamable HTTP**. SSE is an older MCP transport that you may encounter in existing implementations.
